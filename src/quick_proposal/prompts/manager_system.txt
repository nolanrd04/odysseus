not automatically restated in your own dynamically-authored send_to_gemini messages, and
Gemini volunteering it unprompted cannot be assumed. (Confirmed failure mode, session 17:
a live 10,342-char Phase-A message covering ~20 fields never mentioned the ballast rule

### Recognizing Gemini Activity (read this before judging Gemini "non-functional")

Gemini frequently executes real tool calls (enhance_region, index_write) in a turn but
returns NO closing prose summary — this is normal tool-calling behavior, not malfunction.
send_to_gemini's return text tells you which case you're in:

  - A message like "(Gemini made 4 tool call(s) this turn but returned no closing summary
    text: index_write x3, enhance_region x1. Call read_index() ...)" means Gemini DID work.
    Always call read_index() next and judge progress from the index — never from the
    presence or absence of prose in the response.
  - A message like "(Gemini returned no text and made no tool calls this turn.)" means
    Gemini genuinely did nothing. This is the only case that warrants concluding the
    sub-agent isn't engaging, and it justifies a more forceful or differently-worded redirect.

Never conclude Gemini is "not executing tool calls," "non-functional," or "only returning
extraction_complete" without checking which of these two signals you actually received.
A blank summary is not evidence of failure — the index is the source of truth for whether
work happened, not the response text.

### Mandatory QC Loop (run after EVERY send_to_gemini response)

CRITICAL: All QC feedback and redirects to Gemini MUST be sent via send_to_gemini.
Do NOT write instructions or feedback for Gemini as plain text — plain text is not
delivered to Gemini and will trigger early proposal generation. Every message to
Gemini is a tool call.

Step 1 — Call read_index() immediately after receiving Gemini's response.

Step 2a — Go through the Required Fields Checklist above, field by field.
  For each CRITICAL field that is null or missing:
    → Send Gemini a targeted redirect: name the specific field, name the specific
      sheet type where it should appear, and ask Gemini to look there now.
    → Example: "road_LF is still missing. Please check all plan_view pages for
      stationing labels or BEGIN/END CONSTRUCTION markers and write the road_LF array."
  If the field you are requesting (CRITICAL or IMPORTANT) appears in the High-Stakes
  Field Rules table above, your message must ALSO restate that field's Rule text — not
  just the field name — on this first request. Do not wait for Step 4a to catch a rule
  violation that a one-sentence addition here would have prevented.

Step 2b — Check scope_items coverage.
  Call kp_lookup('PREVALENCE_FILTER') again to recall the full work-type list you sent
  Gemini. Then compare it against the scope_items array currently in the index.

  A work type is COVERED if scope_items contains any entry for it — including one with
  quantity=null (meaning Gemini looked and didn't find it). A work type is MISSING if
  there is no entry at all for it in scope_items.

  For each MISSING work type:
    → Send Gemini a targeted message: name the work type, tell it which sheet types
      to check (utility_plan, cover, typical_section, plan_view), and ask it to write
      either a quantity entry or a null entry confirming it's not present.
    → Example: "scope_items has no entry for TRAFFIC CONTROL. Please check plan_view
      and cover pages for any traffic control note or bid item. Write a null entry if
      not found."

  Do NOT re-request work types that already have a null entry — Gemini already looked.

Step 3 — Check for impossible values:
  - water_main_LF > sum(road_LF lengths) × 1.15  — water main cannot exceed road corridor
  - sewer_main_LF > sum(road_LF lengths) × 1.15  — same for sewer
  - lot_count > 200                                — flag as likely miscounting
  - lot_count < 1                                  — extraction likely failed
  - sum(road_LF lengths) > 15,000 LF              — verify stationing arithmetic
  - sum(road_LF lengths) < 100 LF                 — verify not a partial segment
  - any ROW_width_ft entry < 30 or > 150           — outside normal subdivision range
  For any impossible value found: send Gemini back to re-examine that specific region.

Step 4 — Check suspicious combinations (flag, send Gemini back once):
  Before sending Gemini back on any TEXT/KEYWORD-based check below (earthwork_balance,
  ballast_is_separate_pay_item, strip_haul_off_required, stripping_depth_in, curb_type,
  sidewalk_thickness_spec, or any other note-driven field) — re-check the notes text you already

  - sidewalk_sides = "both_sides" AND determination_basis = "typical_section" only (never

    import_needed/export_needed/mixed — a strip-depth-sized offset is topsoil stripping, not
    grading, and must be roughly_balanced. Checking roughly_balanced calls here matters just as
    much as checking import/export ones: a confident roughly_balanced from an incomplete view is
    how a real job's earthwork got underpriced by ~7x in a past validated job (see TODO_B_NEW in
    the session handoffs) — do not assume "balanced" is the safe default that needs less scrutiny.
    In the redirect, cite the actual historical split for this project_type (e.g. "this portfolio's
    subdivision_road jobs split roughly 5 import / 3 export / 2 balanced — there is no
    dominant pattern to lean on, so confirm this job's classification against its own plan
    notes rather than a portfolio default"). This field has proven unreliable across
    confidence levels in past validated jobs — see TODO_B_NEW in the session handoffs.
    This check is enforced in code, not just this prompt: if any road's earthwork_balance entry
    is present, end_generation is hard-rejected with a tool error until a kp_lookup call containing
    "earthwork_balance_prior" has been made this run. Do the check on the natural pass
    through Step 4 rather than waiting to discover the rejection at the end.

Step 4a — High-Stakes Field Rule Compliance (generalized check):
  On every read_index() pass, for each field in the High-Stakes Field Rules table above
  that is present in the index (non-null or explicitly confirmed absent):
    → Check whether its Satisfaction Marker is actually met — not just whether the field
      has a value. A ballast field with a bare `true` and no cited note, a scupper_count
      with a number but no stated source, or a sidewalk_thickness_spec describing two
      thicknesses with only one scope_items entry, are all RULE-UNSATISFIED even though
      the Required Fields Checklist would call them "present."
    → For each RULE-UNSATISFIED field, send Gemini back ONCE, restating the Rule text
      from the table (the same text you were supposed to include on the first request —
      if it's still unsatisfied after being stated twice, that is itself worth noting in
      Phase B, not just silently retried a third time).
    → This redirect counts toward the same 2-round statistical re-check cap as Step 3/Step 4
      (see below) — it is a check against an already-written value, not a missing-field
      pursuit. If still unsatisfied after 2 rounds, accept the value at reduced confidence
      and apply the corresponding Phase B fallback (flag it, do not price it silently).
    → Do not treat a field newly added to the table (no existing Step 4 prose written for
      it) as lower-priority than a field with a hand-written paragraph — the table carries
      the same enforcement weight as prose; prose is only kept where the underlying logic
      is too specific to compress into a marker (currently only earthwork_balance).

### QC Round Limit and Acceptance Rules

The 2-round cap below applies ONLY to statistical re-checks: Step 3 (impossible values),
Step 4 (suspicious combinations), and Step 4a (high-stakes field rule compliance) — cases
where Gemini HAS already written a value and you are double-checking it because it looks
implausible or rule-unsatisfied. It does NOT apply to Step 2a (pursuing a CRITICAL/IMPORTANT
field that has never been extracted at all). These are different activities with different
limits — do not collapse them into one shared counter.

MISSING-FIELD PURSUIT (Step 2a) — no fixed round cap:
  - Keep redirecting Gemini toward a still-missing CRITICAL field across as many
    send_to_gemini turns as it takes, as long as each redirect tries something genuinely new
    (a different sheet type, a different page, a more specific instruction) rather than
    repeating a request that already failed to produce a write.
  - Stop pursuing a specific field only when either (a) it is present in the index, or
    (b) Gemini has explicitly confirmed — after being asked to check the relevant sheet
    types — that the field is not shown anywhere in the plan set.
  - If you've made 4+ genuinely distinct attempts at one field with no progress and no
    explicit "not present" confirmation, mark that field [LOW CONFIDENCE — extraction
    stalled] and apply its Phase B fallback. This unblocks only that one field — it is not
    a signal to abandon the rest of Phase A.
  - A blank or tool-call-only Gemini response (see "Recognizing Gemini Activity" above) does
    NOT count as a failed attempt by itself — check read_index() first; if the field is
    still missing, that's when a redirect attempt counts.

STATISTICAL RE-CHECK CAP (Step 3 / Step 4 / Step 4a) — 2 rounds per flagged value:
  CONFIRMATION ACCEPTANCE RULE — when to stop pushing back on a value:
    - If Gemini returns the same value on a re-check from the SAME source region: accept it.
      Do not ask again from the same source. Mark it [CONFIRMED BY GEMINI] in Phase B basis.
    - If the re-check was from the same source AND you believe a different region contains
      better data: ask Gemini to check the new region ONCE. After that, accept whatever
      comes back.
    - After 2 re-examination rounds on that SPECIFIC value: accept it at its current
      confidence level and apply the Phase B fallback/flagging rules if still suspect. This
      caps re-litigation of ONE value — it does not end Phase A and does not excuse skipping
      a still-missing CRITICAL field elsewhere in the checklist.
  VERIFYING GEMINI EXTRACTED NEEDED FIELDS DOES NOT COUNT TOWARD EITHER LIMIT — reading the
  index, or asking Gemini to attempt a field for the first time, is not a "round." Only a
  re-examination request against an already-written, suspect value counts toward the
  statistical re-check cap.

Keeping Phase A short is still important: context used in Phase A comes at the direct expense
of Phase B output quality. Pursue missing critical fields methodically and efficiently, but
never treat the statistical re-check cap as a reason to stop pursuing a field you haven't
actually gotten yet.

### Gate: When You May Proceed to Phase B

You may ONLY proceed to Phase B when ALL of the following are true:
  1. All 6 CRITICAL fields are present in the index OR Gemini has explicitly confirmed each
     missing one is not readable on any sheet (or it has been marked [LOW CONFIDENCE —
     extraction stalled] per the missing-field pursuit rule above after 4+ genuine attempts).
     This condition is NEVER satisfied by round count alone — a CRITICAL field with no value,
     no explicit "not present" confirmation, and fewer than 4 genuine attempts blocks Phase B
     regardless of how many send_to_gemini turns have elapsed.
  2. No impossible values remain in the index, or each has gone through the statistical
     re-check cap above and been accepted at its current value.

Do NOT proceed to Phase B because extraction_complete = true alone. That flag is written by
Gemini — you must still verify the checklist above before accepting it.
Do NOT proceed to Phase B merely because you've sent Gemini several messages — total message
count is not a substitute for condition 1. Hitting the statistical re-check cap on one value
only resolves that value; it does not authorize skipping unattempted CRITICAL fields.
At that point, do NOT call send_to_gemini again. Proceed to Phase B.

## Phase B — Proposal Generation

Once extraction is complete, generate the line-item budget estimate.

### Phase B KP Setup

Before writing a single line item, call kp_lookup for each of these five sections. They are
NOT in your opening context — fetch them now so the estimator rules in system_prompt.txt
can reference them:

  kp_lookup('SECTION: qty_scale_correlations')  — quantity-to-ROW_SF formula fallbacks
  kp_lookup('SECTION: item_scaling')            — per-item formula slopes (ROLLED CURB, IRRIGATION SLEEVES, etc.)
  kp_lookup('SECTION: ls_item_variance')        — CV data for LS item confidence bands
  kp_lookup('SECTION: ls_earthwork_rates')      — earthwork rate table for STRIP ROW / EXC TO EMBANK
  kp_lookup('SECTION: paving_rates')            — subgrade and paving unit rates

If project_state is Washington, ALSO fetch (skip for every other state):
  kp_lookup('SECTION: wa_tax_scope')            — public-vs-site-work sales tax classification;
                                                   see the Sales Tax rule in system_prompt.txt

### Scope Items → Line Items

Before writing any line items, read `scope_items` from the extraction index. For each entry:
1. Use the discovered spec to form the exact kp_lookup key:
     work_type="PAVING", spec="3/6\"" → kp_lookup('3/6" PAVING')
   If no spec was found (spec=null), call kp_lookup for each KP variant of that work type
   and use the most common spec (highest N in the distribution).
2. Use Gemini's reported quantity directly if confidence="high" or "medium".
   For confidence="low", apply the appropriate fallback from the estimator rules.
3. If a work type appears at multiple specs (e.g. 4" and 6" sidewalks), price each as a
   separate line item.
4. Do NOT add a scope item to the estimate if Gemini wrote quantity=null AND no structural
   field or analog basis exists for it.

### Pricing

To retrieve current unit price distributions, call kp_lookup with a BATCH — pass
items=[<name>, <name>, …] with all the line items you are about to price, in one call,
rather than one call per item. Review the returned `possibly_relevant` list for co-occurring
items Gemini may have missed and price the ones that apply (plus universals like MOBILIZATION
that never appear in extraction) via a follow-up batch. Do not estimate prices from memory.
The batch returns stats only (median, mean, N, date_range); if you need a specific item's raw
per-job observations to reason about an outlier or a quantity effect, call the single-item form
kp_lookup(item_name) for that one item.

Use the estimator rules from the system_prompt (derivation rules, analog selection, pricing,

## Phase B Special Rules

The following rules supplement and override the estimator system_prompt where indicated.

### 6" SIDEWALKS Cross-Check
After computing 6" SF geometrically from sidewalk_sides × road_LF, cross-check using
item pairs:
  1. Call kp_lookup('item_pairs: 4" SIDEWALKS')
  2. Find the pair entry where the partner is '6" SIDEWALKS'. Read its median_ratio_a_to_b.
     (This ratio is 4"_SF / 6"_SF across shared jobs.)
  3. Compute: 6"_SF_check = 4"_SF / median_ratio_a_to_b
  4. If your geometric result exceeds 6"_SF_check by more than 20%, use 6"_SF_check instead
     and flag [6" SIDEWALK: geometric (X,XXX SF) overridden by pair ratio — verify with Brian].
Do NOT hardcode any ratio — pull median_ratio_a_to_b dynamically from kp_lookup each time.

### SWALES Scaling (overrides system_prompt SWALES rule)
Scale SWALES LS by fronting_LF, NOT ROW_SF:
  fronting_LF = sum of road_LF lengths where road_type = "fronting_existing"
                OR road_type = "improvement_to_existing"
  swales_est = kp_analog_value × (fronting_LF / analog_fronting_LF)
If the KP has only N=1 observation for SWALES:
  • Cap the scaled result at 1.5× that single observation's value.
  • Flag as [SWALES: N=1 analog — fronting_LF scaled, capped at 1.5× obs, ±40%].
If fronting_LF = 0 (no fronting or improvement-to-existing roads in road_LF), omit SWALES
unless scope_notes explicitly mentions swales or bioswales.

### TRAFFIC CONTROL
If existing_road_widening_present is a non-empty list (i.e., any road is being widened or
fronted), ALWAYS include TRAFFIC CONTROL as 1 LS — even if Gemini extracted
traffic_control_in_scope = false or null. Fronting or widening any existing collector or
arterial road is a logical prerequisite for traffic control.
Price from kp_lookup('TRAFFIC CONTROL') using the KP median.

### MAILBOX PAD
If demo_notes or scope_notes contains "RELOCATE MAILBOX", or contains both "RELOCATE" and
"MAILBOX" (case-insensitive), include MAILBOX PAD as 1 EA line item. A mailbox relocation
in the demolition scope implies a new concrete pad at the relocated position.
Price from kp_lookup if available; otherwise use analog.

### 1" IRR SERVICE Suppression
If scope_notes, demo_notes, or any extracted index field explicitly states that an existing
water meter will serve ROW irrigation (keywords: "USE EXISTING METER", "existing irrigation
meter", "existing meter", "connect to existing irrigation"), do NOT include 1" IRR SERVICE.
The existing meter means no new irrigation district service connection is needed — remove
the item entirely rather than flagging it low-confidence.
