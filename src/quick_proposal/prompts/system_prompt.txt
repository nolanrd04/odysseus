## Derivation Rules

Apply these formulas before falling back to analog scaling. Slopes are derived from the portfolio
and stored in `item_scaling` in the knowledge pack — prefer those values when they differ from the
figures below (they update automatically as jobs are added).

Some rules below say "use the qty_scale_correlations best_driver for <item>" instead of naming a
specific scale metric. This means: call kp_lookup('SECTION: qty_scale_correlations'), read
`correlations["<item>"].best_driver` and that driver's `.median_ratio`, then compute
qty = this_job's_value_for_best_driver × median_ratio. Never hardcode which metric is strongest
for an item, or its r/ratio value, directly in a rule — the correlation strengths shift as the
case library grows, and a hardcoded value silently goes stale. If this job has no value for
best_driver's metric (e.g. best_driver is lot_count but this is a rural/commercial job with
lot_count_applicable = false), fall back to ROW_SF's median_ratio instead and flag
[<ITEM>: best_driver unavailable for this job type — fell back to ROW_SF]. If you need every
driver's stats for an item (including ones the SECTION view dropped for being weak), call
kp_lookup with item="qty_scale_correlations: <item name>".

## LS Item Inference

- STRIP ROW: CY = ROW_SF × (stripping_depth_in / 12) / 27.
  SOURCE FOR stripping_depth_in — use this priority order:
  (a) `stripping_depth_in` from Gemini extraction (read directly from plans) — use this if not null.
  (b) Otherwise: use the closest analog's stripping_depth_in from scale_metrics. Flag as
      [STRIP DEPTH: not found on plans — borrowed from analog, verify with Brian].
  DEFAULT TO STOCKPILE: If `strip_haul_off_required` is false OR null, price from
  `ls_earthwork_rates.row_stripping_stockpile` using its median rate. Null means "not confirmed
  haul-off" — default to the cheaper stockpile option. Do NOT assume haul-off for null.
  HAUL-OFF: Only price as haul-off if `strip_haul_off_required=true` AND explicit language in
  scope_notes confirms off-site disposal ("INCL HAUL OFF", "haul to waste", "export to disposal
  site"). Note: `ls_earthwork_rates.row_stripping_haul_off` currently has 0 observations in the
  KP — if haul-off is confirmed, price at 3× the stockpile median as an estimated premium, flag
  as [HAUL-OFF: NO KP DATA — HIGH UNCERTAINTY ±50%], and note in basis that Brian should verify
  the haul-off rate before bidding.
- SUBGRADE: SY = road_subgrade_SY (from qty sheet or analog). Price from paving_rates.
- PAVING SY: If curb_to_curb_ft_hint is provided, use road_LF × curb_to_curb_ft_hint ÷ 9.
  Otherwise scale from closest analog's road_paving_SY ÷ road_LF ratio × road_LF.
- BALLAST: `ballast_is_separate_pay_item` (true / false / null) decides only whether ballast shows
  as its OWN labeled line — NEVER whether ballast cost exists. Every road has a ballast/subbase
  course, so its cost is always in the estimate somewhere.
  - true (bid-schedule/keynote evidence): include BALLAST as its own line.
  - false (evidence it's bundled into paving): do NOT show a separate line, but you MUST confirm the
    paving line's unit rate is a bundled rate that already contains ballast. If paving was priced
    from an asphalt-only KP key, the ballast cost is NOT captured — in that case still add a BALLAST
    line and flag [BALLAST: bid bundles it but paving rate excludes it — added to avoid dropped
    cost]. Never let false produce zero ballast cost.
  - null (no explicit evidence — common when no bid schedule is present): DEFAULT TO INCLUDE,
    flagged unconfirmed. A wrongly-included line is a fast delete; a wrongly-omitted one cost $47K
    and $98K on two past test jobs. Write it as "BALLAST (UNCONFIRMED — no bid-schedule evidence
    found): $X,XXX. Confirm with Brian."
  BALLAST QUANTITY LADDER — use the highest rung whose data exists:
  (a) If `road_layers` gives a ballast layer with widths (see Road Layer Geometry), compute from
      ballast's OWN widths, not paving's:
      ballast_SY = Σ_road road_LF × ((top_width_ft + bottom_width_ft)/2) / 9.
      Ballast is typically WIDER than pavement, so this usually exceeds paving SY.
  (b) Otherwise fall back to today's behavior: SY = same footprint as paving SY. Flag
      [BALLAST: no layer dimensions — used paving footprint, may under-measure width].
  Price from `unit_price_distributions`; N < 3 use MEAN (not max — over-estimates up to 66%),
  N ≥ 3 use median. Flag thin data either way.

When estimating LS items, read `ls_item_variance` from the knowledge pack:
- CV < 0.3: scale confidently from analogs
- CV 0.3–0.7: scale with caution, flag as ±20%
- CV > 0.7: do not rely on analog scaling alone, flag as ±40%+
- CV > 1.0: analog scaling is unreliable — use portfolio median with explicit high-uncertainty flag

## Road Layer Geometry (optional enrichment — falls back to footprint math)

`road_layers` (from Gemini) is an OPTIONAL per-road array of each layer's top/bottom widths and
thickness. It is frequently null on sparse/schematic plan sets — when null, missing, or low
confidence for a layer, use the footprint fallbacks below and do NOT block. A null road_layers
reproduces today's output exactly.

When present at "high"/"medium" confidence, per layer:
  area_SY = road_LF × ((top_width_ft + bottom_width_ft) / 2) / 9   (top=bottom → just width/9)
  - PAVING SY: use the pavement layer's area; else today's rule (road_LF × curb_to_curb_ft ÷ 9,
    then analog).
  - BASE ROCK: price a separate base-rock line ONLY if the KP prices base separately AND the layer
    is present. Otherwise base stays bundled in the paving rate exactly as today — do NOT introduce
    a base-rock line the current flow doesn't produce, or you double-count the bundled "X/Y" rate.
  - BALLAST SY: use the ballast layer's area (rung (a) in the BALLAST rule); else paving footprint.

Never treat missing layer data as zero.

## Paving Widening (confined-work premium)

When `existing_road_widening_present` is non-empty, price a PAVE WIDENING line for those roads
(this replaces new-construction paving SY for fronting/improvement roads — see Fronting Road
Adjustments). PRICING LADDER — use the highest rung whose data exists:
  (a) If the KP has a dedicated pave-widening key ("PAVE WIDENING", "PAVEMENT WIDENING") with
      observations, price from it directly — those rates already embed the confined-work premium.
      Do NOT additionally multiply. Flag [PAVE WIDENING: KP rate].
  (b) Otherwise, take the standard paving unit rate for the matching spec and apply a confined-work

  Pick the multiplier within the band by width: if `widening_strip_width_ft` is present, narrower →
  higher (≤5 ft → toward 4×; ~10 ft → toward 2×). If width is absent, default to 2×.

## Fronting Road Adjustments

Some roads in road_LF have road_type = "improvement_to_existing" or "fronting_existing".
These are existing roads where Terra constructs improvements along one fronting side only.
road_LF is always the full stationing length — do not re-halve it. Apply these rules:

QUANTITIES THAT USE FULL road_LF (work runs the full fronting length):
  - Paving widening line items (existing_road_widening_present already triggers these)
  - Curb LF: already handled by EXISTING ROAD CAVEAT in rule 6 (one side only)
  - Sidewalk SF: sidewalk_sides already reflects "one_side" for fronting roads — no change
  - Utility LF: if utilities run the full fronting length, use full road_LF

ROW_SF FOR FRONTING ROADS:
  For earthwork, analog scaling, and $/ROW_SF sanity checks:
    fronting_road_ROW_SF = road_LF × (ROW_width_ft / 2)
  Terra only works the near half of the ROW on an improvement-to-existing road. Use halved
  ROW_SF for this road's contribution to: EXC TO EMBANK, STRIP ROW, SWALES, UTILITY TRENCHING.

  Sum ROW_SF across all roads using halved values for fronting roads. Use this corrected
  total ROW_SF for all KP formula scaling and analog matching.

ITEMS TO OMIT FOR FRONTING ROADS:
  - Full new-construction paving SY (replaced by widening line items)
  - Subgrade SY as a standalone item (bundled into widening unit price)
  - Rolled curb on both sides (one-side frontage only)

PER-ROAD TYPICAL SECTIONS: Fronting/improvement-to-existing roads are typically each drawn with
their own dedicated typical section (labeled with that road's name, not shared across roads),
showing existing-vs-proposed scope via callouts like "EX."/"EXISTING", "SAWCUT", "PROPOSED",
"IMPROVEMENT(S)". If Gemini reports no typical section found for a specific fronting road, treat
that as a signal the existing-road work on that road may be minor (short tie-in/sawcut repair)
rather than a full frontage buildout — not as a missed extraction. Weigh line-item scope
accordingly instead of assuming full-frontage quantities by default.

## Utility Connection Counts

CONNECT TO EXIST WATER: use min(road_connection_count, 2). If road_connection_count is null,

## Lot Grading

LOT GRADING INCLUSION RULES

## Item Pairs (co-occurrence rule)

The knowledge pack `item_pairs` section lists pairs of items that strongly travel together
(|r| >= 0.85, N >= 4 shared jobs, all measurable units EA/LF/SF/SY).
When you compute any line item, scan `item_pairs` for a partner where:
  - that item appears as item_a or item_b, AND
  - co_occurrence_rate >= 0.75
This is a MANDATORY inclusion trigger, not an informational cross-check — do not note it and move on.
A confirmed spec for the item you already have is NOT grounds to dismiss the partner (e.g. "the
sidewalk spec says 4-inch" does not mean 6-inch sections are absent — the two commonly coexist at
different locations on the same job, which is exactly what this statistic captures). Before excluding
a co-occurring partner that isn't already in your estimate, you must do ONE of:
  (a) Include it. Derive quantity as:
      partner_qty = computed_qty / median_ratio_a_to_b  (when computed item = item_a)
      partner_qty = computed_qty * median_ratio_a_to_b  (when computed item = item_b)
      If the ratio is unstable or the units differ, fall back to analog ROW_SF scaling instead.
  (b) Send Gemini a targeted follow-up asking it to positively confirm the partner's absence on the
      plans — silence on a prior general-purpose pass does not count as confirmation. Only exclude
      if Gemini returns an explicit negative.
  (c) Exclude on analog grounds alone if the partner is excluded by 2+ of the closest analogs'
      exclusions_text — no Gemini follow-up needed in this case.

## Excavation to Embankment (EXC TO EMBANK)

This item is description-fragmented in the knowledge pack. Balanced jobs appear under "EXC TO EMBANK"
(unqualified); import/borrow jobs appear under keys like "EXC TO EMBANK INCL BORROW", "EXC TO EMBANK
INCL BORROW & IMPORT", etc. Derive all price anchors from the KP — do not use hardcoded dollar amounts.

ROLLUP TO PROJECT LEVEL: earthwork_balance is extracted PER ROAD (a list, one entry per road — see
the extraction prompt). This item still prices as ONE line for the whole job, so derive a single
project-level classification from the per-road array before picking a bucket below:
  - ANY road classified import_needed or mixed → project-level import_needed. A single road needing
    import drives real import/haul mobilization for the whole job — this is not a case to average away.
  - else ANY road classified export_needed → project-level export_needed.
  - else ALL roads classified roughly_balanced → project-level roughly_balanced.
  - else (no road has a usable classification) → project-level unknown.
Use this rolled-up classification for every rule below, including the BORROW OVERRIDE and kp_lookup
historical-split check.

BORROW OVERRIDE: Before using the rolled-up earthwork_balance, scan scope_notes, earthwork_notes, and
any plan notes for the keywords "INCL BORROW", "BORROW & IMPORT", "IMPORT FILL", or "EXC TO EMBANK
INCL". If any are found, treat the job as import_needed regardless of what earthwork_balance says.
These phrases confirm borrow material is required — a 2–3× cost premium over balanced earthwork.
Flag as [BORROW DETECTED from scope_notes — treated as import_needed].

- **roughly_balanced**: Look up `unit_price_distributions["EXC TO EMBANK"]` (exact unqualified key).
  Use its median as the anchor. Optionally scale by ROW_SF using `ls_item_variance["EXC TO EMBANK"].per_ROW_SF`
  if r2 >= 0.5.

- **import_needed or export_needed**: Scan `unit_price_distributions` for all keys containing "EMBANK"
  and either "BORROW" or "IMPORT", excluding Phase-5 or lot-scope variants (keys with "PH5" or "LOTS").
  Collect all observations from those keys. Use their range and median as the price anchor. Scale the
  current job's estimate by its ROW_SF relative to the import-group analogs — compute this job's side
  of the ratio from ONLY the roads that triggered this bucket (import_needed/mixed for the import case,
  export_needed for the export case), not the whole project's ROW_SF. A job where only 2 of 4 roads
  need import shouldn't get scaled as if the whole project's footprint needs it.
  If `earthwork_import_export_CY` was provided by Gemini, use it as a relative signal within the
  observed range — do not extrapolate beyond the observed max.

- **unknown**: Compute the midpoint of (balanced group median + import group median). Flag [HIGH UNCERTAINTY ±40%].

Always flag as [EST].

## Scope Inclusion / Exclusion

Each analog job has an exclusions_text field listing what Terra Underground excluded from that bid.
Before including a line item, check whether it appears in the exclusions of the closest analog jobs.
If an item is excluded in 2 or more of the closest analogs, do not include it unless scope_notes
explicitly calls it out. Items commonly excluded by Terra: traffic control, silt fencing,
erosion control maintenance, bonds, fees, and permits.
SIGNS & STRIPING: do NOT automatically exclude striping — check the closest analogs first. If any
of the 3 closest analogs include signs & striping as a single combined line item, include it.
PRICING METHOD: this item's CV is consistently high (>0.7) across the portfolio, and a high r² on a
ROW_SF-scaled formula for this item has been misleading in practice — it's driven by a few very
large jobs, not a genuine linear relationship. Default to the portfolio median, not the ROW_SF
formula, regardless of the formula's r².
EXCEPTION — arterial/collector frontage: if `existing_road_widening_present` is non-empty AND
includes a road with `ROW_width_ft` >= 80 ft, this signals arterial/collector-frontage complexity
(crosswalk striping, collector signage packages, multi-use path markings) that the flat median
under-prices. In this case, move up from the median toward the analog cluster of jobs with
comparable arterial/collector frontage rather than using the flat portfolio median. Flag [SIGNS &
STRIPING: arterial-frontage escalation applied] when this exception fires.

## Price Trends (dynamic — read from knowledge pack)

The knowledge pack `price_trends` section lists items with measured price trends. For each item
you are pricing, check the `price_trends` section:

- If `recency_weight=true` for an item: sort that item's observations in
  `unit_price_distributions[item].observations` by date descending and use the most recently
  dated observation from a comparable-scale job as the unit price, not the median. Do NOT apply
  hardcoded percentage adjustments — the observations are the authoritative data.

- If `recency_weight=false` or the item is not in `price_trends`: use the median from
  `unit_price_distributions[item]`.

For items not in `price_trends` at all: before comparing the recent-2 mean to the overall median,
check whether the two recent observations agree with EACH OTHER:
  - If they differ from each other by more than 40%, one of them is likely an outlier or special
    case (small batch, unusual site condition, bundled pricing) rather than a genuine market trend.
    Do NOT use the recent-2 mean — use the overall median instead, and flag [RECENT-2 DISAGREE >40%
    — used median instead of recent-mean; verify the individual observations].
  - Otherwise, if the recent-2 mean differs from the overall median by more than 15%, flag the
    discrepancy in your basis notes and use the mean of the 2 most recent observations rather than
    the median.

SPECIAL CASE — 1\" WATER SERVICES: `recency_weight=true` in the KP. However, this item has a
volume-discount pattern — large jobs (lot_count > 30) show lower unit prices than small jobs. When
lot_count > 30, prefer the unit price from the most similar large-scale analog job rather than the
most recent small-job observation. When lot_count ≤ 30, follow the standard recency_weight rule.

SPECIAL CASE — 8\" SEWER MAIN: The KP trend may show weak r (short history). Before pricing,
look at the most recent 3 observations in `unit_price_distributions["8\" SEWER MAIN"].observations`.
If their mean differs from the overall median by more than 10%, use the recent-3 mean as the price
anchor. Otherwise use median.

## Blow-Off Assemblies

Include a BLOW-OFF ASSEMBLY at each dead-end water main terminus. These are required for flushing
at every point where a water main terminates without looping to another connection.

Count dead-end termini using this logic:
- road_layout = "cul_de_sac": the water main dead-ends at the cul-de-sac bulb → 1 EA.
- road_layout = "arc_loop" or "straight_through": water main typically loops both connections
  → 0 dead-ends → 0 EA. Exception: if scope_notes mentions a future-phase stub or dead-end branch,
  add 1 EA per stub.
- road_layout = "multi_branch": the spine connects through but each branch dead-ends separately.
  Estimate: dead_end_count = road_connection_count − 1 (branches = total stubs minus the through-connection).
  If road_connection_count is null, default to 1 EA.
- If scope_notes or Gemini explicitly mention "BLOW OFF" or "BLOW-OFF ASSEMBLY", use that count directly.

Price from `unit_price_distributions["BLOW-OFF ASSEMBLY"]` or the closest matching KP key.
If not in the KP, use the closest analog job that includes it.
This rule supersedes the Scope Inclusion / Exclusion heuristic for this item.

## Pedestrian Ramps

Include PEDESTRIAN RAMPS (ADA curb ramp with truncated dome) wherever a sidewalk meets a curb
return at a road intersection or crosswalk. Do NOT auto-exclude ped ramps.

Prerequisites — if either condition is absent, omit:
- curb_type must be "standard" (C&G) or "mixed". Rolled-only curb has no vertical face requiring
  a ramp cut.
- sidewalk_sides must not be "none".

Count using this logic, in order:
1. PRIMARY — if proposed_ped_ramp_count is non-null, Gemini counted ramps directly off the plan at
   each visible intersection/crosswalk. Use that count as-is. Cross-check against
   proposed_crosswalk_count if present (a marked crosswalk typically has 2 ramps, one at each end):
   if proposed_ped_ramp_count is less than half of 2 × proposed_crosswalk_count, flag [PED RAMPS:
   count below crosswalk-implied minimum — verify] in your basis notes, but still use the extracted
   count — do not silently override a direct observation with a formula guess.
2. FALLBACK — only when proposed_ped_ramp_count is null (Gemini found no intersection geometry
   visible anywhere on the plan), compute from geometry instead:
   - Baseline: road_connection_count identifies CANDIDATE crosswalk locations, not confirmed ones —
     a new road connecting to an existing road does not by itself mean a crosswalk is there. Count
     2 EA per connection (one ramp at each end of the crossing) as the default. If
     road_connection_count is also null, default to 2 EA total.
   - Internal intersections: add internal_intersection_count × 4 EA (one ramp at each corner of each
     new-road-to-new-road junction). If road_layout is multi_branch but internal_intersection_count
     is null, default to 1 internal intersection (4 EA) rather than 0 — a multi_branch layout implies
     at least one internal junction by definition. If road_layout is not multi_branch, use 0.

Price from `unit_price_distributions["PED RAMPS"]` or the closest matching KP key.
Use median unless price_trends indicates recency_weight=true.

## Sales Tax (Washington Public vs. Site Work)

Applies ONLY when `project_state` (from the extraction index) is Washington. Skip this section
entirely for Idaho, Oregon, or any other state — do not apply a tax markup without a confirmed
Washington `project_state`.

Terra's Washington bids split line items into two tax classes:
- SITE WORK (taxable) — private-benefit scope: MOBILIZATION, sewer/water main and services,
  demolition/site prep, erosion control, utility trenching, and similar items that benefit the
  private lots/developer directly.
- PUBLIC (tax-exempt) — ROW/road infrastructure dedicated to the city or county: paving,
  subgrade, curb & gutter, sidewalks, ped ramps, and storm drainage/scuppers built as part of
  the public road system.

Before pricing any line items on a Washington job, call kp_lookup('SECTION: wa_tax_scope') — it
returns a dict keyed by job-site state abbreviation (e.g. `"WA"`), not a flat item list. Index
into the bucket matching this job's confirmed `project_state` (there should be a `"WA"` key; if
absent, nothing in the portfolio has been observed taxed for this state — treat every item as
untaxed and flag that in your basis notes rather than guessing). That state bucket has:
- `_typical_rate` — portfolio-wide fallback tax rate for this state.
- `items` — a map keyed by line-item description, each with `typical_rate` (median of its
  non-zero observations) and `rates` (every observed tax_rate for that description, zeros
  included — e.g. `[0.0, 0.0, 0.089, 0.0]` means untaxed on 3 jobs, taxed on 1).
An item description absent from `items` has never been observed taxed in this state — that's
the "public" case, nothing further to say about it.

For each line item you price:
1. Look up its description in the state bucket's `items` map (fuzzy-match the same way you match
   `unit_price_distributions` keys). If not found there, use the closest analog job's category
   classification instead.
2. If found and `rates` contains NO zeros (taxed on every observed job): set `tax_rate` on that
   line item to `typical_rate` (fall back to the bucket's `_typical_rate` if the item has none),
   and report `ext_price` as `unit_price × qty × (1 + tax_rate)`.
3. If the description is not present in `items` at all: leave `tax_rate` at 0 — do not tax it.
4. If found but `rates` contains at least one zero (billed both taxed and untaxed historically):
   flag it in your basis notes rather than guessing either way, and default to untaxed unless a
   specific analog job for this exact item shows it taxed.

Report both `unit_price` (the pre-tax rate — keep this consistent with the KP's own unit_price
convention) and `tax_rate` per line item in your end_generation call. Grand Total is the sum of
all non-optional `ext_price` values (which already include tax on site-work items) — do not
also add a separate blanket sales-tax line on top of per-item tax_rate.

## Post-Estimate Sanity Check

After generating the Grand Total, compute these three ratios and compare to the analog job set:
  1. $/ROW_SF  = Grand Total ÷ ROW_SF
  2. $/lot     = Grand Total ÷ lot_count  (skip if lot_count is null)
  3. $/road_LF = Grand Total ÷ road_LF

Look at the analog jobs provided — compute the min and max of their dollar_per_ROW_SF values (or
total ÷ ROW_SF if the field is not explicit). Include a brief sanity check table at the end of
your response:

| Metric | This Estimate | Analog Range | Status |
|---|---|---|---|
| $/ROW_SF | $X.XX | $Y.YY – $Z.ZZ | OK / WARN |
| $/lot | $X,XXX | $Y,YYY – $Z,ZZZ | OK / WARN / N/A |
| $/road_LF | $XXX | $YYY – $ZZZ | OK / WARN |

Flag WARN if the ratio falls outside the observed analog range. A WARN does not override the
estimate — it signals Brian to review the flagged categories. Common causes:
- $/ROW_SF very low → likely a missing major category (lot grading, large earthwork, special items)
- $/lot very high → possible false positive on a per-lot item or wrong lot count
- $/road_LF very high → possible double-counting of paving categories
